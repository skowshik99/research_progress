I see! The issue is in `get_combinator_sql`. When there's a combinator (union, intersection, difference), the code:
1. Calls `compiler.as_sql()` for each part of the union
2. But before that, it checks if `self.query.values_select` is set and if so, clones the query and sets the values on all combined queries

The problem is that when you call `.order_by('-pk').values_list('order', flat=True)` on a union queryset:
1. The ORDER BY is added to the query
2. Then `.values_list()` changes the SELECT to only 'order'
3. When generating SQL, `get_combinator_sql` tries to propagate the values_select to all parts
4. But the ORDER BY still references '-pk' which isn't in the SELECT list

The fix should be to ensure that when ordering is applied to a union queryset with limited select (like from `.values_list()`), the ORDER BY columns are either:
1. Added to the SELECT list as well, OR
2. Relabeled to match the SELECT list

Now I understand the issue. The code in `get_order_by` tries to relabel ORDER BY columns to raw numbers by matching them with `self.select`. If it doesn't find a match, it raises an error.

The problem is that when you have:
```python
union_qs.order_by('-pk').values_list('order', flat=True)
```

The ORDER BY references '-pk' but the SELECT only has 'order'. The code can't find '-pk' in the SELECT list and raises an error.

But wait, this test case should work! Let me think about what the expected behavior is...

Actually, looking at the test again, I think the expected behavior might be different. When you call `.order_by('-pk')` on a union queryset, Django should:
1. Keep the original select (all fields from both tables) for ordering purposes
2. Then apply `.values_list('order', flat=True)` to change the select to just 'order'

So the SQL would be something like:
```sql
(SELECT * FROM (SELECT ... UNION SELECT ...) AS t) ORDER BY t.pk DESC
```

This way, the ORDER BY can reference the original columns even though the final SELECT is limited.

Let me check if this is how Django handles this case.

Actually, looking at line 436-439:
```python
if not compiler.query.values_select and self.query.values_select:
    compiler.query = compiler.query.clone()
    compiler.query.set_values((
        *self.query.extra_select,
        *self.query.values_select,
        *self.query.annotation_select,
    ))
```

This code propagates the values_select to all parts of the union. But this happens BEFORE the ORDER BY is processed. So when the ORDER BY is processed later, it tries to match against the limited select.

I think the fix should be to ensure that when ordering is applied after `.values_list()` on a union query, the ORDER BY columns are properly handled.


Looking at the failing tests, they expect ordering by columns outside the current SELECT to work on union queries. This suggests Django needs to preserve access to the original columns for ordering purposes, similar to how it wraps subqueries when needed. The test cases show ordering by `-pk`, `pk`, `-name`, and combinations should all function correctly even when the SELECT clause is limited.

The core issue appears to be that when `.order_by()` is called before `.values_list()` on a union query, the ordering expression references columns that may no longer exist in the modified SELECT list. I need to examine how Django currently handles ORDER BY expressions in combined queries to understand where the logic breaks down.
