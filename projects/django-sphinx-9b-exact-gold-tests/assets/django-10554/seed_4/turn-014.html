Now I understand the issue. The problem is in the `get_order_by` method of the SQL compiler. When you have a union query and you call `order_by()` on it, the code tries to relabel ORDER BY columns to raw numbers (like '1', '2', etc.) by matching them with columns in `self.select`.

But there's an issue - when you use `.values_list()` or `.values()` on a union queryset, the SELECT clause might contain expressions that don't match what the user wants to order by. For example:

```python
union_qs = qs1.union(qs2)  # This selects all fields from both tables
union_qs.values_list('order', flat=True).order_by('-pk')  # User wants to order by 'pk' but only 'order' is selected
```

In this case, the code can't find 'pk' in the SELECT list and raises an error.

Wait, looking at the test again:

```python
(union_qs.order_by('-pk').values_list('order', flat=True), [-1, 6, 5, 7]),
```

Here, the user calls `order_by('-pk')` first, then `values_list('order', flat=True)`. So the ORDER BY happens before values_list.

Let me trace through what happens:
1. `union_qs` is created from `qs1.union(qs2)` - this clears ordering and limits
2. `union_qs.order_by('-pk')` adds '-pk' to the ordering
3. `.values_list('order', flat=True)` changes the select to just 'order'

The problem is that after calling `values_list()`, the ORDER BY references a column ('pk') that's not in the SELECT list.

Actually wait, let me re-read the test more carefully:

```python
(union_qs.order_by('-pk').values_list('order', flat=True), [-1, 6, 5, 7]),


```

This creates a queryset where the ORDER BY is applied to the original union result, then only 'order' is returned. But if I look at the failing test:

```python
test_union_with_values_list_on_annotated_and_unannotated
```

This one has annotations involved. Let me check what the actual error was:

```
django.db.utils.DatabaseError: ORDER BY term does not match any column in the result set.
```

So the issue is that when using annotations in a union, the ORDER BY clause can't find the annotated column because it's not in the SELECT list. The annotation gets added to the query but isn't being properly referenced in the ORDER BY clause for combined queries.

Looking at the test setup, `qs1` uses `annotate()` with `Exists(ReservedName.objects.filter(order=OuterRef('num')))`, while `qs2` is a simple filter. When these are united, the annotation needs to be preserved across both sides of the union, but the current implementation doesn't handle this correctly.

The error suggests the ORDER BY clause is trying to reference a column that wasn't actually included in the SELECT statement. This typically happens when an annotation is used in ORDER BY but isn't explicitly selected, or when the annotation structure differs between the two querysets being combined. I should examine how the compiler processes the UNION operation to see where the mismatch occurs.
