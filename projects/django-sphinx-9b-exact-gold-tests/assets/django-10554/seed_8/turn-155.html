Let me think about this problem more carefully. The issue is that when you have a combined query with ordering, and then call values_list on it, the ordering columns need to be in the SELECT list of each subquery.

Looking at the test case:
```python
(union_qs.order_by('-pk').values_list('order', flat=True), [-1, 6, 5, 7]),
```

The flow is:
1. `qs1.union(qs2)` creates a union query
2. `.order_by('-pk')` adds ordering to the union query
3. `.values_list('order', flat=True)` sets values_select to ('order',)

When generating SQL for the combined query:
1. `get_combinator_sql` is called
2. For each subquery compiler, we call `compiler.as_sql()` which calls `pre_sql_setup()` -> `get_order_by()`
3. In `get_order_by()`, it tries to resolve the ordering expression '-pk' but the subquery doesn't have 'pk' in its SELECT list

The fix should ensure that before calling `compiler.as_sql()`, we add the ordering columns to the subquery's SELECT list (as extra_select).

But there's another consideration. When the database doesn't support ORDER BY in compound queries (like SQLite), each subquery needs to have its own ORDER BY clause. In this case, we need to wrap each part in a subquery and add ORDER BY inside the subquery.

Actually, looking at the code more carefully, I see that the check at line 420-421:
```python

    ...
    if compiler.get_order_by():
        raise DatabaseError('ORDER BY not allowed in subqueries of compound statements.')
```

This checks if any of the individual subqueries have their own ordering BEFORE we modify them. So if we set `compiler.query.order_by` before this check, it will fail.


After the check passes, I can set `compiler.query.order_by` to apply the main query's ordering. Then when `compiler.as_sql()` runs, it generates SQL with that ordering applied. The key is ensuring the ordering columns exist in each subquery's SELECT list before calling `as_sql()`. I'll add them to extra_select using RawSQL expressions and let Django handle the rest. But I'm realizing the real problem might be how `get_order_by()` resolves those ordering expressions—it needs to match against the SELECT list correctly.

When `OrderBy.resolve_expression` is invoked on a subquery, it attempts to resolve each source expression against that subquery's schema. If the subquery lacks certain columns from the main query, resolution fails. The solution requires adding ordering columns to each subquery's SELECT list beforehand so resolution succeeds.
