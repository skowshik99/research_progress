The problem is in the `get_order_by` method of the compiler. Let me look at that code again:


This code iterates through `self.select` and tries to find a match for the ORDER BY expression. If no match is found, it raises an error.

The issue is that when you do `.values_list('order', flat=True)` on a UNION query, the SELECT list only contains 'order'. Then when you try to order by 'pk', there's no match because 'pk' is not in the SELECT list.

But wait, looking at the test case again:
```python

```

This test expects ordering by '-pk' even though 'pk' is not in the SELECT list. 

I think the real issue is that Django should add the ordering column back into the SELECT list when needed, rather than failing. For UNION queries specifically, the ordering needs to reference the original table columns since the combined result doesn't preserve individual column information across all parts of the union. The problem appears to be how UNION operations handle ordering after applying .values_list(). When you chain .values_list('order', flat=True) followed by .order_by('-pk'), the SQL generation fails because it tries to order by a column that's been excluded from the select list.

Looking at the failing test cases, there are two problematic patterns: calling .order_by() before .values_list(), and calling .order_by() after .values_list(). Both scenarios attempt to order by columns that don't appear in the final SELECT clause, which causes the database to reject the query.

The first case works fine since 'pk' remains available for ordering before values_list filters it out. The second case fails because values_list has already removed 'pk' from the select list, leaving nothing to order by. This suggests the fix might involve ensuring that columns used in ORDER BY clauses remain accessible even after .values_list() is applied, or handling the ordering differently for UNION queries where column visibility becomes ambiguous.
