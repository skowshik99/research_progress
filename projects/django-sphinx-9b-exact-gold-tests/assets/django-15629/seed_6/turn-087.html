Let me take a step back and think about this more carefully. The issue is that when altering a PK field's collation, we need to also update FK columns in other models that reference it.

Looking at the test case:
1. Pony model has an id field (CharField primary key)
2. Rider model has a pony_id foreign key to Pony.id
3. We alter Pony.id to have db_collation='nocase'
4. After the alteration, both Pony.id and Rider.pony_id should have the collation 'nocase'

The problem is that the AlterField operation only alters the field on the Pony model. It doesn't know about the Rider model or its pony_id field.

I think the solution is to modify the state_forwards method to also update any FK fields that reference the altered field. When the state is updated, the FK fields should automatically get the correct collation from their target fields.

Actually, looking at the ForeignKey.db_parameters() fix I made earlier, the FK field should already propagate the collation from its target field. But the issue is that the FK field's db_collation attribute is not set - it's only added to db_parameters().

Wait, let me re-read my fix:

```python
def db_parameters(self, connection):
    db_params = {"type": self.db_type(connection), "check": self.db_check(connection)}
    # Check if the target field has a collation (e.g., CharField with db_collation).
    # If so, propagate it to the FK column. This is required for databases like MySQL
    # where the FK column must have the same collation as the referenced column.
    if getattr(self.target_field, "db_collation", None):
        db_params["collation"] = self.target_field.db_collation
    return db_params
```

This adds the collation to db_parameters(), which is used when generating SQL for creating/altering columns. 

But when we're altering an existing column, the schema_editor.alter_field() method needs to use the new field's db_parameters() to generate the ALTER COLUMN statement. Since the FK field doesn't have its own db_collation attribute, I need to ensure it gets one. The real issue is that the ForeignKey field itself needs to store the collation, not just pass it through during SQL generation.
