I see. The test creates Pony without collation, Rider and Stable with FK to Pony, then alters Pony.id to have collation. The FK columns (pony_id in Rider and pony_id in Stable) should also get the collation.

The issue is that when we alter a PK field's collation, the FK columns pointing to it need to be updated. Let me trace through the code path:

1. `AlterField.database_forwards()` calls `schema_editor.alter_field()`
2. `alter_field()` calls `_alter_field()`
3. In `_alter_field()`, when `drop_foreign_keys` is True (which happens when the PK type changes), it updates related fields

But wait, looking at line 1029-1030:
```python
if drop_foreign_keys:
    rels_to_update.extend(_related_non_m2m_objects(old_field, new_field))
```

This only adds related fields if `drop_foreign_keys` is True. Let me check what `drop_foreign_keys` is set to.

Looking at lines 826-833:
```python
drop_foreign_keys = (
    self.connection.features.supports_foreign_keys
    and (
        (old_field.primary_key and new_field.primary_key)
        or (old_field.unique and new_field.unique)
    )
    and old_type != new_type
)
```

So `drop_foreign_keys` is True when:
1. The connection supports foreign keys
2. Both old and new fields are primary keys OR both are unique
3. The types are different

In this case, we're changing the collation of a CharField, not the type. So `old_type == new_type` and `drop_foreign_keys` is False. This means `rels_to_update` is empty and the FK columns aren't being updated.

I need to add logic to handle collation changes separately from type changes. 

The fix needs to check for collation differences independently and update FK columns whenever the collation changes, regardless of whether the type itself changed.
